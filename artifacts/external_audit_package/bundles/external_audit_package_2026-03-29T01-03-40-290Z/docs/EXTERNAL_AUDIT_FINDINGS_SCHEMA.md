# External Audit Findings Schema

## Purpose

This schema defines the minimum structured format required for findings returned
by a real external auditor.

## Required fields

| Field | Type | Purpose |
| --- | --- | --- |
| `audit_session_id` | string | Identifies the external handoff session |
| `auditor_profile` | string | One of the profiles in `docs/EXTERNAL_AUDIT_PROFILE_MATRIX.md` |
| `finding_id` | string | Stable identifier for the finding |
| `severity` | enum | `blocker`, `material_issue`, `note`, `no_issue` |
| `category` | enum | `reproducibility_failure`, `documentation_ambiguity`, `semantic_overclaim`, `theory_runtime_collapse`, `governance_weakness`, `no_issue` |
| `finding_domain` | enum | `technical`, `semantic`, `documental`, `theoretical`, `overclaim`, `legibility` |
| `location` | string or array | Exact file, command, artifact, or bundle path |
| `reproduction_steps` | array | Minimum steps required to reproduce or inspect the issue |
| `observed_behavior` | string | What the auditor actually observed |
| `expected_behavior` | string | What the auditor expected instead |
| `evidence_refs` | array | Exact files, commands, hashes, or bundle ids supporting the finding |
| `boundary_risk` | string | How the finding could create overread, ambiguity, or invalid interpretation |
| `minimal_correction` | string or null | Smallest correction that would address the finding |

## Severity meanings

- `blocker`: the issue prevents a credible external audit or invalidates the
  package as a reproducible handoff
- `material_issue`: the issue does not fully block review, but it undermines
  trust, interpretation discipline, or traceability in a non-trivial way
- `note`: the issue is real but does not force a system change by itself
- `no_issue`: the auditor explicitly checked a scoped surface and found it
  acceptable

## Category meanings

- `reproducibility_failure`: the pinned package cannot be reproduced or
  commands do not run as specified
- `documentation_ambiguity`: a doc, manifest, or handoff step leaves material
  room for misreading
- `semantic_overclaim`: wording overstates what the runtime, corpus, or package
  establishes
- `theory_runtime_collapse`: the package allows a prohibited inference between
  theory and implementation
- `governance_weakness`: authority, freeze, or branch/package discipline is too
  weak or ambiguous
- `no_issue`: the checked surface is acceptable within the stated scope

## Example record

```json
{
  "audit_session_id": "external_audit_2026-03-26_profile_reproducibility_01",
  "auditor_profile": "technical_reproducibility",
  "finding_id": "EXT-REP-001",
  "severity": "material_issue",
  "category": "documentation_ambiguity",
  "finding_domain": "documental",
  "location": [
    "docs/EXTERNAL_AUDIT_SETUP.md",
    "external_audit_package_manifest.json"
  ],
  "reproduction_steps": [
    "Read the setup doc.",
    "Follow the listed command order.",
    "Compare the generated package id against the manifest."
  ],
  "observed_behavior": "The setup doc allows a reader to look for a manifest before the build step is run.",
  "expected_behavior": "The setup doc should state that the manifest is generated by the package build step.",
  "evidence_refs": [
    "package_id=external_audit_package_2026-03-26T23-12-31-269Z"
  ],
  "boundary_risk": "The auditor may assume the package is pre-generated and mis-pin the repos.",
  "minimal_correction": "State the build-first rule before the pinning step."
}
```

## No-issue report rule

If an auditor finds no issue in a scoped review, the auditor should still return
one structured record with:

- `severity = no_issue`
- `category = no_issue`
- the exact scope that was reviewed
- the exact SHAs and package id that were reviewed

## What does not satisfy this schema

The following do not satisfy the schema:

- an email or chat message saying "looks fine"
- an oral opinion with no written record
- a list of vague concerns with no exact location or scope
- a screenshot with no file, command, or bundle reference

## Interpretation boundary

This schema governs reporting discipline only. It does not determine whether a
finding is true by itself. Truth, severity, and required changes are decided by
the intake and triage process.
